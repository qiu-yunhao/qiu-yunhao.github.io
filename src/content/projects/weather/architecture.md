# Weather 架构设计

## 分层方案

项目采用 `data / domain / presentation` 三层结构：

- `data` 层负责远程接口、本地数据库、偏好存储和数据映射
- `domain` 层负责领域模型、仓库接口和用例封装
- `presentation` 层负责 Compose UI、页面状态、导航和主题

这样的分层让 UI、业务逻辑和数据来源之间的职责更清晰，也方便后续继续扩展功能。

## 数据层

数据层同时处理远程数据和本地数据：

- 远程部分通过天气 API 获取实时天气、预报、空气质量和生活指数
- 本地部分通过 `Room` 保存城市与缓存天气数据
- 偏好设置通过 `DataStore` 保存语言、主题、温度单位和当前城市等信息

数据层还承担 DTO、实体和领域模型之间的映射工作，避免上层直接依赖接口返回结构。

## 领域层

领域层主要负责把能力组织成可复用的业务单元：

- 定义天气、城市等领域模型
- 约束仓库接口
- 提供获取天气、管理城市、读取偏好的用例

这样做的好处是，页面层拿到的是面向业务的结果，而不是零散的数据操作细节。

## 表现层

表现层基于 `Jetpack Compose` 构建，结合 `ViewModel`、`StateFlow` 和导航管理页面状态：

- 首页负责展示当前天气和关键信息卡片
- 预报页负责承载每日、逐时、空气质量和生活指数视图
- 城市页负责城市切换和管理
- 设置页负责语言、主题和单位偏好

项目还通过 `Hilt` 管理依赖注入，使 `ViewModel`、仓库和数据源的连接关系更稳定。

## 为什么这样组织

这个项目不是一次性的界面练习，而是希望在后续继续叠加功能。因此我更看重：

- 可读性：新功能接入时能快速定位代码位置
- 可扩展性：新增模块不会直接破坏原有页面
- 可维护性：状态来源、数据流向和职责边界都足够明确
